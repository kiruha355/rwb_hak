Все восемь локально рассчитанных blob совпадают со значениями **ранее сохранённого коллегой** [source-tree.json](../../corpus/01_olist_identity/evidence/source-tree.json). Повторный GitHub tree API вернул `403 rate limit exceeded`, поэтому это сравнение с tree evidence коллеги, а не собственное успешное открытие дерева. Git master по `ls-remote` сейчас указывает на `d9e49802f3e92d09ee94ab9ccc5e457f207a8959`; [commit](https://github.com/olist/work-at-olist-data/commit/d9e49802f3e92d09ee94ab9ccc5e457f207a8959) действительно меняет reviews, но этим не объясняется содержательная разница версий. Совпадение байт с tree evidence не доказывает bytes в DB/raw; SQL/DB не запускались.

Фактическая CSV-проверка на этом снимке: все восемь предложенных ключей непусты и уникальны; orders→customer и item→order/product/seller, payment→order, review→order имеют 0 отсутствующих ссылок. Все 99 441 `customer_id` orders различны и покрывают customers; 96 096 distinct `customer_unique_id`, 250 имеют несколько **ZIP prefixes**, а не доказанных переездов. Это не SCD история и не доказательство назначений офис/подарок. Сохранить исходную связь и адрес customer_id с заказом — рекомендация; будущие исправления и историчность требуют нового контракта.

Reviews: 99 224 непустые уникальные пары, 98 410 ID, 789 ID связаны с несколькими orders, у 547 orders несколько строк; для tuple пяти полей payload конфликтов по ID нет при буквальном сравнении CSV-строк. Поэтому entity+bridge восстанавливает этот снимок при сохранении всех связей и условной FD; pair fact тоже сохраняет его, но дублирует payload. Ни один вариант не гарантирован для следующих загрузок: проверять конфликты, пустые значения и не делать молчаливый dedup. Вес влияет на ответ: средний score **4.0864206240 по парам** против **4.0888019510 по review_id**, каждый ID получает один голос во втором случае. Вес по заказам — третье определение и требует политики для нескольких reviews. Нельзя утверждать split-cart survey, NPS или повторный ответ только из FD/cardinality.

Категории: в локальном CSV 610 products без категории, 73 непустых исходных категории, среди них `pc_gamer` и `portateis_cozinha_e_preparadores_de_alimentos` не имеют перевода. При группировке delivered item price получены 74 группы, включая пустую, и сумма 13 221 498.11; исходное `beleza_saude` — 1 233 131.72. Отсутствующий перевод не равен отсутствующей категории. Это проверка CSV, не готовый Q5 в модели.

## Деньги: тот же набор, разные предикаты

Для 98 665 заказов с обеими сторонами, все статусы, независимо сложены `payment_value` и `price + freight_value`, затем `delta = payments − items`. Денежные поля CSV здесь непусты; использован Decimal. Источник регламента не задаёт причину несовпадений.

| Предикат на delta | Заказов | Сумма delta этих же заказов |
|---|---:|---:|
| `delta != 0` | 639 | −1 819.51 |
| `abs(delta) > 0.01` строго | 366 | −1 818.84 |

Сумма абсолютных delta = 7 981.47; net скрывает взаимную компенсацию. Реконструкция «366 по порогу + сумма всех delta» возможна, но исходный SQL профиля неизвестен; не приписываем её автору. Есть 775 orders с payment без items, один с items без payment, neither = 0; суммы наблюдаемых сторон соответственно 162 591.95 и 143.46. Отсутствие child — неизвестное/неприменимое значение, не автоматически ноль, даже если downstream специально выберет нулевую гипотезу. Должны учитываться все четыре coverage-класса, NULL/zero, знак, точность, исключение/включение ровно 0.01, и delivered-отдельно. [PostgreSQL 16 numeric](https://www.postgresql.org/docs/16/datatype-numeric.html) документирует точный decimal; [aggregates](https://www.postgresql.org/docs/16/functions-aggregate.html) возвращают NULL для пустого `sum` и игнорируют NULL в `avg`. Это документация, не runtime тест модели.

Прямое соединение items×payments даёт на пересечении 117 601 строки; item+freight **15 848 099.68 → 16 571 528.43**, payment **15 846 280.17 → 20 308 134.71**. Это собственный расчёт по кратностям, не реальный SQL join. Отдельные факты не предотвращают плохой join автоматически. В [Hudasf](https://github.com/hudasf/Olist-Dashboard-Streamlit/blob/b9fd7a8bd79515e284980fbefe226c0b2dbf5838/olist_dataAnalyst.py#L29-L33) items включены в `allorder_df`, затем [L109–129](https://github.com/hudasf/Olist-Dashboard-Streamlit/blob/b9fd7a8bd79515e284980fbefe226c0b2dbf5838/olist_dataAnalyst.py#L109-L129) добавляет payments и суммирует их; пример не выполнялся. B07-007 ссылается на неверные L452–462: фактический sum payment по категории находится на [L414–422](https://github.com/tolamoye/Olist-E-commerce-Data-Analysis/blob/c609dfa753e84ebeca0711344a650668f4e81652/Olist%20data.sql#L414-L422). Ошибка locator не отменяет существования примера, но её нельзя наследовать.

## Q1–Q3: что показывают альтернативы

[Tasks Q1](https://github.com/daniilivanovp-droid/hackathon-students/blob/3da32d149bfa14dca3fdb0c5863d0771c38efbfc/docs/tasks.md#L5-L17) задаёт purchase period и предлагает выбрать условия выручки; статус population для **числа заказов** отдельно явно не задан. На CSV в этом периоде 99 421 всех против 96 478 delivered; выручка `sum(item.price)` delivered за весь снимок = 13 221 498.11, все delivered попадают в это окно. Пустой ноябрь — наблюдение, календарь — предложение для отчёта; ноль подходит для известного пустого месяца данной выборки, не для неизвестного внешнего периода.

Q2 для продавца `4869f7a5dfa277a7dca6462dcf3b52b2`: item price delivered = 226 987.93; distinct order count всех статусов = 1 132 против 1 124 delivered. Период Q2 не установлен Q1 автоматически. Число продавцовских заказов может пересекаться между продавцами: суммы distinct по продавцам не обязаны равняться distinct всей площадки.

Q3 delivered: средний по 96 478 orders с items `sum(price+freight)` = **159.8754498 → 159.88**; средний по 96 477 orders с payments = **159.8563572 → 159.86**. Все статусы с имеющейся соответствующей стороной: **160.6251712 / 98 666** и **160.9902667 / 99 440**. 159.88 поддерживает выбранную интерпретацию, но без перечисления population, времени, компонентов и политики missing не доказывает единственное допустимое определение. Для delivered отсутствующий payment у одного заказа означает разные знаменатели; не заменять его нулём. Зафиксировать отдельно `item_revenue` и `order_item_plus_freight` — предложение, а не бухгалтерская выручка и не доказанный cash collected.

## Время, платежи, выкуп и источники

В CSV 2016-11 пуст; 2018-09 содержит 16 orders, 2018-10 — 4, в обоих месяцах delivered status 0. Max purchase `2018-10-17 17:30:18`, max присутствующая delivery `2018-10-17 13:22:46`; они не устанавливают as-of, полноту событий или причину хвоста. [NIST о цензурировании](https://itl.nist.gov/div898/handbook/apr/section1/apr131.htm) описывает общий случай известного окончания наблюдения, но не устанавливает его для Olist. Не утверждать «точная цензура на 31 августа», обязательный 90-day cohort или нулевую зрелость как доказанный факт. При известной границе в будущем показывать недостаточно наблюдённые ячейки unknown, с условиями и знаменателем.

[DDL исходного проекта](https://github.com/kiruha355/rwb_hak/blob/2f0a8de45aadc3b685f434aaaf736f0cca7c7f2e/scripts/init/02_raw_ddl.sql#L46-L55) называет `payment_sequential` номером платежа внутри заказа, `payment_installments` числом частей; payment CSV содержит только order ID, sequential, type, installments, value — отдельной даты исполнения каждого взноса нет. Сам факт поля не доказывает фактическое поступление денег, даты погашения, settlement или ledger. `delivered` — наблюдаемый статус доставки/интерпретация для кейса, не факт отсутствия последующего возврата, полноценного «выкупа» или данных корзины. Восьми файлов недостаточно для анализа refunds, отмен корзины, marketplace take rate и точного cashflow; это ограничение полей/таблиц, а не утверждение, что события никогда не происходили.

## Короткий shortlist и сильные возражения

1. Зафиксировать file manifest/хеши и затем сверить фактический raw; без этого нет доказательства воспроизводимого входа. Не выдавать совпадение с коллегиным tree за собственное открытие API.
2. Сохранить независимые grain и coverage; сравнивать деньги на order-level, точным типом, не предполагать zero для missing. Неправильный join и смешение фильтров уже дали измеримые контрпримеры.
3. Согласовать Q1/Q2 counts и Q3 чек с явно показанными альтернативами; 3.12% покупок по всем статусам нельзя неявно превратить в delivered-only.
4. Сохранить review связи и выбрать вес; оба варианта представления годятся **условно**, а не навсегда. Проверить конфликты следующих загрузок.
5. Считать delivery proxy и поля платежей по их наблюдаемому значению; не приписывать бизнес-причины, движения адресов, точный as-of или возвраты.

**Готово для защиты с границами:** восемь конкретных файлов и локальные hashes/counts; ключи/FK в этом CSV; две версии comparator и 4 coverage-класса; вычисленный fanout; buyer unique ID как интерпретация задания с ограничениями адреса; pair vs entity+bridge при проверенной FD; результаты Q1–Q3 только с указанными фильтрами; отсутствие per-installment даты в схеме. Ни один пункт не доказывает работу core/mart или соответствие DB/raw.

**Открытые вопросы организаторам / источнику:** (1) официальный URL, авторитетный регламент, дата и канал появления Q6–Q10/вброса, расхождение баллов PDF/текст; (2) статус/период для counts Q1/Q2, Q3 сумма/знаменатель и допустимость отсутствующей стороны; (3) смысл «выкуп» при отсутствии returns/refunds и что включает выручка/доставка; (4) as-of и полнота каждого события; (5) лицензия именно распространяемых CSV и производных. Наблюдения и предложения не равны ответам на эти вопросы.
