## Проверяемые вопросы до выбора

- RQ05: точно ли сохраняются значения денег и отсутствие значения; как проверить независимо суммы и покрытие двух разных отношений? Альтернативы: `numeric` без scale, фиксированный scale с явной политикой допустимого округления, binary float. У какого варианта добавление третьего знака и `NaN` обнаруживается, а не меняет данные молча?
- RQ06/10: откатывает ли одна ошибка ВСЮ сборку и останавливает ли клиент с ненулевым кодом? Можно ли второй раз собрать модель без дрейфа значений, прав и потери чужих зависимостей? Сравнить recreate, фиксированные объекты с перезаполнением, versioned swap; явно проверить права и границу разрушения.
- RQ17: один ли input snapshot дают восемь таблиц при обновлении raw, когда загрузчик применяет `TRUNCATE`; позволяют ли filename и время восстановить исходные байты? Сравнить запрет конкурентной загрузки, предварительные блокировки и согласованный снимок с изоляцией по умолчанию.
- RQ21: переживут ли проверки новые статусы, NULL, источники и возможный будущий grain без потери данных? Какие нарушения — blocker, какие наблюдения качества? Сравнить строгие ограничения с диагностикой и карантином; известные неупорядоченные даты не должны быть причиной отбрасывания.

## Adopt candidate: контракты, а не результат выполнения

1. **Клиент и транзакция.** Предложение: `psql -X -v ON_ERROR_STOP=1 -1 -f model/build.sql` с настройкой `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;` как первой инструкцией файла; без собственных `BEGIN/COMMIT/ROLLBACK` и команд вне транзакции. `-1` применим к `-f/-c`; `-X` отключает psqlrc; обработчик обязан проверить код выхода. Отдельно предусмотреть недоступное подключение, commit error и обрыв связи с неизвестным итогом; повторная проверка нужна, а не предположение об откате. Документация: [psql, Options и Exit Status](https://www.postgresql.org/docs/16/app-psql.html), [SET TRANSACTION](https://www.postgresql.org/docs/16/sql-set-transaction.html), [Transactions §3.4](https://www.postgresql.org/docs/16/tutorial-transactions.html). Нельзя выдавать консольный exit 0 за корректность содержимого.
2. **Согласованность raw.** [Изоляция §13.2](https://www.postgresql.org/docs/16/transaction-iso.html): READ COMMITTED даёт разные snapshots между запросами, REPEATABLE READ удерживает снимок для обычных MVCC-данных. Но [TRUNCATE Notes](https://www.postgresql.org/docs/16/sql-truncate.html) прямо описывает исключение: старый snapshot может увидеть таблицу пустой. Загрузчик в базовом коммите делает `TRUNCATE` каждой таблицы и далее COPY: [load_raw.py:121–138](https://github.com/kiruha355/rwb_hak/blob/2f0a8de45aadc3b685f434aaaf736f0cca7c7f2e/scripts/load_raw.py#L121-L138), транзакцию запускает [строки 182–201](https://github.com/kiruha355/rwb_hak/blob/2f0a8de45aadc3b685f434aaaf736f0cca7c7f2e/scripts/load_raw.py#L182-L201). Кандидат: операционно исключить reload на весь build; если это нельзя гарантировать — захватить совместимые с SELECT, но конфликтующие с TRUNCATE блокировки всех восьми raw таблиц **до формирования snapshot и чтения**, единым предсказуемым порядком, затем REPEATABLE READ; проверить на изолированной fixture два порядка гонки. При ожидании предусмотреть timeout и отказ. Блокировки требуют прав и могут задерживать loader; DDL/прочие источники параллелизма проверить отдельно. [LOCK](https://www.postgresql.org/docs/16/sql-lock.html), [explicit locking §13.3](https://www.postgresql.org/docs/16/explicit-locking.html). Не утверждаем, что это уже проверено или что всякая raw-перезагрузка безопасна.
3. **Типы.** Для денег кандидат — `numeric` с контролем формата/конечного значения и явно выбранной политикой scale; фиксированный `numeric(p,2)` округляет лишние знаки перед проверкой переполнения, потому сначала проверять исходное значение, а не считать cast проверкой отсутствия потерь. `numeric` допускает специальные значения; регламент конечных сумм нужен отдельно. [Numeric §8.1.2](https://www.postgresql.org/docs/16/datatype-numeric.html). Наивные даты сохранять как `timestamp without time zone` до подтверждения временной зоны источника; тип `timestamptz` для строки без зоны использует session TimeZone, а при преобразовании в `timestamp without time zone` зона в исходном значении игнорируется. Контракт будущих offset-bearing значений проверять отдельно. [Date/time §8.5.1.3](https://www.postgresql.org/docs/16/datatype-datetime.html), [functions §9.9](https://www.postgresql.org/docs/16/functions-datetime.html).
4. **Ограничения.** PK исходного grain только после проверки данных и согласования контракта; `review_id` один не подходит по профилю. `CHECK` пропускает NULL, `UNIQUE` по умолчанию допускает повтор с NULL, nullable FK по умолчанию допускает отсутствие ссылки; `NOT NULL`, `NULLS NOT DISTINCT` или `MATCH FULL` применять по смыслу, а не механически. FK не запрещает заказ без дочерних строк; не делать обязательный INNER JOIN. [Constraints §§5.4.1–5.4.5](https://www.postgresql.org/docs/16/ddl-constraints.html). Chronology anomalies и пропуски — quality flags/числа, не hard CHECK и не исправление значений. Невалидный cast — blocker с идентификатором строки/поля; это отдельный класс от допустимого, но подозрительного порядка дат.
5. **Проверки до commit.** Для обязательного blocker использовать явный `RAISE EXCEPTION`, в том числе если результат проверки неизвестен; `ASSERT` может быть отключён параметром `plpgsql.check_asserts`, а warning не останавливает транзакцию. [PL/pgSQL §43.9](https://www.postgresql.org/docs/16/plpgsql-errors-and-messages.html). Понятные counters и примеры аномалий не должны подменять исключения для потери строк и ключей. Отдельный журнал warning надо сохранять после успеха; сообщения откатной транзакции не равны durable отчёту.
6. **Provenance.** В manifest вне raw фиксировать source repo + immutable ref, URL каждого файла, SHA-256 байтов, header и число строк, загрузчик/version, дата/время и версию build SQL, затем — counts по каждой таблице и договорённую форму reproducible сравнения. `_source_file` и `_loaded_at` полезны, но не доказывают хэш/первичный commit; download использует mutable master и пропускает непустые локальные файлы: [download_data.sh:9–32](https://github.com/kiruha355/rwb_hak/blob/2f0a8de45aadc3b685f434aaaf736f0cca7c7f2e/scripts/download_data.sh#L9-L32). Без связи манифеста с загрузкой нельзя утверждать, что запущенная raw соответствует CSV. Открытый pin для входного набора, соответствие исходных CSV raw и семантика timestamps пока unresolved.

## Альтернативы и последствия

| Выбор | Плюсы | Ограничения / применение |
|---|---|---|
| Транзакционный recreate явно принадлежащих объектов | простой запуск с нуля и откат при SQL-ошибке при корректном wrapper | `DROP SCHEMA ... CASCADE` может удалить объекты других схем; схемы/объекты требуют ownership, новые объекты могут потерять grants и зависимости. [DROP SCHEMA](https://www.postgresql.org/docs/16/sql-dropschema.html), [Privileges §5.7](https://www.postgresql.org/docs/16/ddl-priv.html). Допустимо только в выделенном согласованном scope; raw никогда не удалять/не менять. Список зависимостей/прав — предварительная проверка, а не обещание безопасности. |
| Существующие таблицы, атомарное перезаполнение | может сохранить идентичность объектов и права | усложняются миграции схемы и порядок FK, TRUNCATE блокирует и имеет MVCC-исключение; нужна проверка rollback и совместимости потребителей. Не доказано предпочтение в текущем окружении. |
| Versioned schema + переключение | потенциально даёт проверку нового набора до переключения | управление ссылками, grants, concurrent readers и очистка старой версии сложнее; наличие атомарного switch здесь не доказано. Отложить до реальной необходимости. |

Права builder: SELECT на raw, необходимые права в выделенном core/mart, без изменения raw; роль владельца raw или superuser не обеспечивает защиту от случайной записи, даже если код её не содержит. Доказать effective permissions и отсутствие обходов на тестовой роли. Не выполнять GRANT/REVOKE в этом исследовании. При наличии неизвестных внешних зависимостей — blocker до решения scope; каскад не разрешается как универсальный способ исправить ошибку.

## Предлагаемая матрица проверок и counterexamples

Все ниже — **proposed**, только изолированная fixture, не текущий raw. Распределение по колонкам и точный SQL зависят от утверждённой модели.

| Вставленный случай / этап | Ожидание и acceptance check |
|---|---|
| Чистая сборка, затем повтор из неизменного input | оба запуска 0; равны counts, ключевые множества, поля и финальные decimal суммы в каждом grain; сравнение с NULL-aware semantics, отдельно разрешённые метаданные run time. Snapshot и порядок генерации ключей зафиксировать; порядок SELECT без ORDER BY не гарантирован. |
| Ввод невалидной даты/суммы, `NaN`, слишком большой или третий decimal знак | невалидный cast/недопустимая величина вызывает ненулевой exit и полный rollback; 3-й знак по принятой политике либо сохраняется без потери, либо явно блокируется. Повторить с нарушением в конце, сравнить старую core, grants и отсутствие частичной новой сборки. |
| Начало старого заказа, дата отгрузки раньше покупки; NULL delivery | строки и исходные даты сохранены; quality flag/counter увеличивается, отсутствующая дата остаётся NULL; build успешен, если иной обязательный контракт не нарушен. |
| Дубликат `(order_id, order_item_id)`; NULL части ключа; orphan item | выявить конкретный ключ и блокировать либо явно согласованный карантин с полным accounting. Проверить, что обычный UNIQUE и nullable FK не принимаются как достаточные. |
| Заказ без items, без payment, без review; item с NULL freight и item с нулём | заказ сохранён; missing child, NULL и истинный 0 различимы; sums и counts показывают все классы, а не затираются `COALESCE`. `sum` над отсутствующими значениями сам по себе NULL: [aggregate functions §9.21](https://www.postgresql.org/docs/16/functions-aggregate.html). |
| 2 items и 3 payments в одном заказе | прямой join даёт 6 строк; сверять payments и items после независимого агрегирования по order_id. В reconciliation вывести оба totals, число строк, число NULL, отсутствующие стороны, population/status, знак и scale. Расхождение не приписывать причине и не блокировать только из-за несовпадения без утверждённого бизнес-контракта. |
| Один review_id на 2 заказа с разными payload; 2 reviews на один заказ | pair или bridge обязаны сохранить оба payload/связи, иначе blocker; возможный grain ещё не утверждён. |
| Новый статус/категория; добавлена новая опциональная колонка | неизвестный статус не исчезает при JOIN; исходное значение доступно, policy подсчёта ещё не утверждена. Добавленный атрибут отдельно учесть в input inventory и принять решение об обработке; факт загрузки старого набора не доказывает поддержки нового. |
| Конкурирующий loader и build | проверить оба порядка, ожидание/timeout, отсутствие смешанного набора и фиксацию идентификатора поколения. Тест без специально организованной конкуренции ничего не докажет. |
| Принудительная ошибка после DDL и в финальной проверке; запуск без прав на raw write | fail-fast, ненулевой exit, предыдущая core сохраняется при откате, raw не изменён, успешный build на разрешённой роли. При разрыве во время COMMIT outcome устанавливается повторной инспекцией. |

Для каждого из 8 raw-источников: входной count = сохранённые detail + явно учтённые исключения (при допущенной агрегации справочника — отдельно mapping и coverage); множества ключей в обе стороны, duplicates/nulls, anti-joins по обязательным FK, независимые суммы исходных полей и NULL counts до/после. Сверка глобальной суммы сама по себе не ловит компенсирующие ошибки, перестановку связей и утрату полей. Декомпозиция не предполагает, что будущая модель обязана иметь ровно 8 fact tables.

## Later / reject / unresolved

- **Later:** versioned swap и incremental/CDC: только при измеренной потребности и наличии события/версии; снимок не восстанавливает исторические изменения.
- **Reject как универсальное утверждение:** просто `CREATE IF NOT EXISTS` обеспечивает идемпотентность; `DROP ... CASCADE` безопасен; любой `ASSERT` обязателен; транзакция всегда гарантирует единый raw snapshot с `TRUNCATE`; жёсткий `CHECK` хронологии; `COALESCE(...,0)` для каждого пропуска; float для точной денежной сверки; сумма payments обязана совпадать с items+freight. Они сохранены как отрицательные направления, а не приписаны конкретному агенту.
- **Unresolved:** время/зона source, договор scale/округления и допустимых нечисловых значений, лицензия CSV, pinned hashes фактически загруженных восьми файлов, фактические права и зависимости, comparator и coverage 366 расхождений, конкретный treatment будущих source schema changes. Control 159.88 и другие цифры не определяют population однозначно.

## Pipeline доказательств для команды и жюри

1. Зафиксировать задачи/решения человека и вывод ИИ с версиями; собрать manifest и проверить получение inputs. 2. Эксперт проверяет grain, ключи, population и каждый SQL по первичным требованиям; статический review — отдельный этап. 3. На изолированной fixture прогнать позитивные и негативные случаи, конкурентность и rollback; сохранить команды, исход фикстур и результаты без выгрузки raw. 4. С согласованным runtime отдельно собрать реальный вход, сохранить коды, counts, reconciliation и quality warnings; затем проверить ответы из core/mart. 5. Другой reviewer воспроизводит на тех же входах, подтверждает конкретные claims и документирует расхождения. Результат в этом пакете — **только чтение документации и исходников**, не fixture/provider/DB PASS и не финальный research review.
