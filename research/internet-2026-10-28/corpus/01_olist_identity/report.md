## Buyer и адрес

Фактически прочитано 99 441 строк customers; `customer_id` непуст и уникален, `customer_unique_id` непуст, различных 96 096. У 250 unique ID более одного ZIP **prefix**. См. [скрипт и агрегаты](evidence/observed.json); эти измерения не доказывают связь каждой строки с ровно одним заказом, поскольку orders не парсились. [Kaggle API description](https://www.kaggle.com/api/v1/datasets/view/olistbr/brazilian-ecommerce) описывает данные; доступный непосредственно через API текст не содержит полного словаря колонок. Вторичный [словарь сообщества, раздел customers](https://github.com/aduverger/olist/blob/master/data/README.md#olist_customers_dataset) описывает `customer_id` как связь с заказом и `customer_unique_id` как идентификатор покупателя; его статус вторичный, а не официальный словарь.

**Adopt candidate:** идентичность для межзаказного анализа — unique ID; сохранять адресные атрибуты исходного customer_id вместе со связью к заказу. **Альтернатива:** единственный ZIP в измерении покупателя — потеряет разные наблюдения или потребует явно выбранного правила. **Reject:** считать 250 покупателей переехавшими или восстановить SCD-историю: отличаются только префиксы, причины и временной порядок не установлены. **Proposed check:** соединить orders→customers, проверить cardinality, непокрытые ключи и сохранение всех адресов на каждой загрузке; не выполнен.

## Review-pair против entity + bridge

[Собственный streaming read](evidence/reproduce.py), сравнение точных декодированных значений, в том числе пустых строк: 99 224 записи, 98 410 distinct review ID; 789 ID встречаются с несколькими заказами, у 547 order ID несколько строк. 99 224 различных непустых пар `(review_id, order_id)`; повторов пары нет. Для каждого из пяти полей `review_score`, `review_comment_title`, `review_comment_message`, `review_creation_date`, `review_answer_timestamp` число review ID с конфликтом — **0**, как и для полного tuple. Три ограниченных примера разных пар одного ID с hash payload — в [observed.json](evidence/observed.json); конфликтных примеров нет. Равенство относится к этому файлу и правилам сравнения, не к будущим данным и не к SQL NULL semantics.

**Adopt candidate:** хранить каждую пару как факт с исходным payload — простая побайтово-логическая реконструкция строк, но payload повторяется; подсчёт по парам и по отдельным ID даёт разные веса. **Альтернатива также допустима для этого снимка:** entity по review ID с пятью полями + bridge по уникальной паре; join entity→bridge восстанавливает каждую строку при проверенной FD. Entity нельзя заполнять `DISTINCT ON review_id` без проверки FD: при будущих конфликтах такая операция потеряет значения. Тогда нужно хранить payload на паре/версионировать сущность или явно блокировать и расследовать загрузку; решение не предопределено. Обе схемы допускают fanout при присоединении нескольких отзывов и других многозначных фактов к заказу; мера должна быть агрегирована на своём grain. Не следует считать повтор ID дублем или объяснять его survey/NPS/split-order без источника. **Proposed checks:** уникальность и непустота пары, FD всех пяти полей с NULL-aware сравнением, полный round-trip rows и контроль cardinality; проверки SQL ещё не выполнены.

## Категории

На четырёх CSV измерены 32 951 разных product ID без повторов; 610 товаров с пустой категорией, 73 непустые категории; 71 ключ перевода без повторов; две категории товаров без ключа перевода — `pc_gamer`, `portateis_cozinha_e_preparadores_de_alimentos`. Детали и headers — [observed.json](evidence/observed.json). **Adopt candidate:** различать «категория отсутствует» и «известная категория без перевода», сохраняя исходное имя; **reject:** внутреннее соединение с переводом либо общий unknown для обоих случаев. **Proposed check:** сохранение всех продуктов и категорий, отдельный отчёт отсутствующих переводов; не выполнен в БД.

## Неизвестное и дальнейшие проверки

- Официальный полный словарь столбцов через открытый Kaggle API не найден; вторичная копия — ориентир, не первичное доказательство. Уточнить у организатора значение и историю полей.
- Независимо проверить Kaggle/Git содержимое по файлам, историю предыдущего review-файла, права и применимые условия. API дерева GitHub при повторном обращении вернул `HTTP Error 403: rate limit exceeded`; ранее дерево и blob были успешно получены. HTML Kaggle при web open не отдал текст; прямой API работал.
- Периоды наблюдения и завершённость событий нельзя вывести из одного снимка; определить as-of и censoring по метрике, получить источник полноты. Проверка временного окна и причин хвоста не выполнена.
- Четыре оставшихся файла не проходили CSV parsing; клиентские связи и total 550759 требуют отдельной проверки. Core/mart, бизнес-семантика и production behavior не проверены.
