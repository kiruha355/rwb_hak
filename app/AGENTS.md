# app/ — веб-дашборд «Скажите «мяу»»

Рабочий инструмент аналитика поверх нашей модели: обзор, продажи, доставка и раздел
«Данные и модель» (путь raw → core → mart, проверки, ответы 1–10, формулы).
Все цифры берутся **только из `mart`/`core`**, никогда из `raw`
(`raw` читается лишь в обозревателе модели, чтобы показать исходную строку).

Общий контекст проекта: [../idea/CODEX_HANDOFF.md](../idea/CODEX_HANDOFF.md), правила команды: [../AGENTS.md](../AGENTS.md).

## Как запустить

1. Запустить Docker Desktop. Если порт 5432 занят чужим контейнером `fast-vpn-db`, проверить `docker ps`.
2. Поднять базу (из корня репозитория): `bash scripts/setup.sh`.
3. Собрать модель (core + mart), около 2–2,5 минут на полных данных:
   ```bash
   RWB_RAW_RELOAD_PAUSED=1 RWB_DB_MODE=docker COMPOSE_PROJECT_NAME=rwb_hak bash scripts/build-model.sh build
   ```
4. Один раз установить зависимости: `npm install` в `app/api` и в `app/web`.
5. Запустить API: `node app/api/server.js`.
6. Запустить фронт: `npm --prefix app/web run dev` и открыть http://localhost:5173.

Если API перезапускать не хочется, а данные в базе изменились: `POST /api/cache/clear`.
Python на этой машине: `C:/Users/HONOR/python.exe` (у MSYS-python нет pip). Shell — Git Bash на Windows.

## API: эндпоинт → источник

| Эндпоинт | Что отдаёт | Читает |
|---|---|---|
| `/api/meta` | штаты, категории, месяцы, статус сборки | `core.fact_order`, `core.dim_category`, `core.dim_date`, `core.check_results` |
| `/api/overview` | KPI и ряд по месяцам (календарь, пустые месяцы = 0), повторные покупатели | `mart.v_orders`, `mart.v_order_items`, `mart.v_order_delivery_variants`, `core.dim_date` |
| `/api/delivery` | вовремя/опоздал + оценки, штаты, этап задержки, корзины дней | `mart.v_orders` + `mart.v_order_delivery_variants` |
| `/api/late-orders` | 60 самых долгих опозданий | то же |
| `/api/commerce?limit=10\|25\|50\|100` | категории, топ продавцов, платежи | `mart.v_order_items`, `core.fact_payment` + `mart.v_orders` |
| `/api/model` | карта raw→core, ключи, колонки, зависимости витрин, баланс строк | каталог PG, `pg_depend` |
| `/api/table/:schema/:name` | первые строки таблицы (белый список) | raw/core |
| `/api/view/:name` | SQL витрины + 30 строк | `pg_get_viewdef` |
| `/api/trace/:orderId` | строки одного заказа во всех слоях | raw, core, mart |
| `/api/checks` | самопроверки и аномалии | `core.check_results`, `core.data_issues` |
| `/api/metrics` | паспорта метрик | `mart.metric_definitions` |
| `/api/answers` | Q1–Q5 + контрольные цифры | `mart.q01…q05` |
| `/api/answers-b` | Q6–Q10, все варианты | `mart.q06…q10`; если витрин нет → `{available:false}` |

Общие фильтры у бизнес-эндпоинтов: `from`, `to` (YYYY-MM), `state`, `category`.

## Определения (не менять без решения команды)

| Метрика | Правило | Контроль |
|---|---|---|
| Выручка `item_revenue` | `sum(price)` позиций заказов `delivered`, без доставки | 13 221 498,11 |
| Средний чек | среднее по **заказам** delivered от `price + freight` | 159,88 |
| Покупатели | `count(distinct customer_unique_id)` по всем заказам | 96 096 (окно Q1: 96 090) |
| Опоздание | вручение позже обещанной **календарной даты** | 6,8 % (по времени было бы 8,1 %) |
| Этап задержки | продавец передал позже `shipping_limit_date` или задержка после передачи; «виноватых» не называем | 27,8 % / 72 % |

Неаддитивны (в итогах пересчитываются, а не суммируются): средний чек, покупатели,
доли опозданий, средняя оценка, медиана дней. Аддитивны: выручка, заказы, единицы.

## Дизайн: что пользователь уже решила

- Это **профессиональный инструмент аналитика**, а не мобильное или «фитнес»-приложение. Информация важнее стилизации.
- Шрифт **IBM Plex Sans** (моно — IBM Plex Mono только для id). Не возвращать Manrope, Rubik, моно-цифры: «выглядит нейронно».
- Нейтральные белые панели, тонкие рамки, скругления 6–8 px. Верхний ряд KPI однотонный.
- Цвета: графит `#1f2226`, один акцент синий `#2f7fb8`, песочный для сравнения. **Никакого красного и зелёного**, никакого тёмного фона с фиолетовым.
- Боковое меню — обычный список с иконками и короткими подписями, **не «таблетки»**.
- Слева сверху — название команды **«Скажите «мяу»»** и «Аналитика маркетплейса», не «Capibara».
- Меньше текста, но у каждой цифры понятная подпись; формулы — в подсказке «i».
- Обязательно: выгрузка CSV у блоков, ссылка на текущий вид (фильтры и настройки в URL), сортируемые таблицы.
- Обзор и Продажи не должны дублировать друг друга: Обзор = главные цифры и динамика, Продажи = из чего складывается выручка.

## Как проверять изменения

1. `npx tsc --noEmit -p app/web` — без ошибок.
2. Открыть страницу в браузере при ширине около 1440 px (при узком окне включается мобильная раскладка).
3. Графики Recharts анимируются: снимок сразу после загрузки бывает пустым, подождать 2–3 секунды.
4. Цифры сверить с контрольными (таблица выше) и с `/api/answers`.

## Известные пробелы

- Витрины `q06–q10` есть в базе, только если модель собрана из ветки Mput `t3/integrate-q6-q10-marts` (шаг `model/55_answers_block_b.sql`). Из `main` они пока не собираются, и вкладка «Блок Б» покажет подсказку.
- История категорий (SCD2, вброс) в модели не сделана. Когда `mart.v_order_items` начнёт брать категорию на дату заказа, страница «Продажи» подхватит это без правок фронта.
- Круговая зависимость импортов уже была: `lib.tsx` не должен импортировать `Filters`/`Page` (поэтому `Page` — отдельный файл).
