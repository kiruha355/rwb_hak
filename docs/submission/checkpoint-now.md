# Capibara: выступление на две минуты

## Речь

Мы строим аналитическую модель маркетплейса Capibara на настоящих данных Olist. Начали с восьми CSV: выяснили, что означает строка, проверили ключи, связи и пропуски. Исходный слой raw сохраняем; ответы считаем через нашу модель core и витрины mart.

Модель содержит четыре отдельных факта: заказ, товарная позиция, платёж и связь отзыва с заказом. Их объединяют семь справочников. Покупателя определяем по customer_unique_id; адрес сохраняем в контексте заказа. Все связи отзывов сохраняются, а аномалии получают признаки без исправления догадками.

Почему нельзя просто соединить всё? В реальном CSV-заказе одна позиция, три платежа и один отзыв. Товар стоит 29,99, доставка — 8,72; сумма заказа и платежей — 38,71. Прямое соединение повторит товар трижды и покажет 89,97. Поэтому сначала агрегируем каждый факт до заказа. Это пример из CSV, ещё не результат core.

Выручка — стоимость товаров доставленных заказов без доставки. GMV заказа включает доставку; средний чек считаем по заказам. Для первых двух вопросов показываем обе совокупности, для второго–пятого используем весь снимок.

HTML показывает полный экспорт коллеги: 99 441 заказ из core и mart, 14 сверок с SQL. Отдельно на 1 000 настоящих заказов проверили исходные строки, 201 условие сохранности, повторную сборку и откат. Полную привязку CSV к raw и lifecycle с последними исправлениями ещё проверяем.

Дашборд посвящён выполнению заказов, сервису, продажам и качеству. Также подготовлена стратегия развития. Следующий шаг — полная сверка сохранности и оставшиеся вопросы.
