## Подтверждённые дефекты проверки

### R1 — P2: fixture пропускает неверные средние и числовые доли

**Места:** `answers/q06-q10/test_fixture.py:59–64`, `:71–77`, `:80–89`.

Основные результаты Q7/Q9/Q10 — средние сроки/число частей и доли опозданий — не защищены проверками значений:

- Нет ни одного assertion для `avg_delivery_days`, `avg_installments_all_types`, `avg_installments_credit_card`, `avg_installments`.
- Единственный assertion для `late_pct` проверяет NULL у недоставленного заказа с оценкой 3 (`:87`). Числовая доля нигде не проверяется.
- Для Q10 не проверяется ни `duration_denominator`, ни `late_denominator`.

**Контрпример на существующей fixture:** в delivered/timestamp Q7 восемь известных сравнений, все восемь — опоздания; правильная доля `8/8*100 = 100`. Замена знаменателя в `q07.sql:21` на `count(*)` дала бы `8/9*100 ≈ 88.8889`, и все нынешние assertions Q7 сохранились бы. Для Q9 в покупках 2018 части платежей `[1,1,1,0]`: средняя `0.75`, по кредитной карте `[1,0]`: `0.5`. Возврат нуля или `-999` в этих средних также не обнаруживается.

**Малая выполненная проверка:** AST исходного теста скомпилирован в памяти; его неизменённые assertions `59–64`, `71–73`, `76–77`, `80–89` исполнены на специально сконструированных Python-результатах. Они прошли при `avg_delivery_days=-999`, средних рассрочки `-999`, неправильных числовых `late_pct` и неправильных знаменателях Q10. Это проверка чувствительности assertions, а не исполнение SQL или всего PostgreSQL fixture.

**Минимальный fix:** добавить числовые assertions на перечисленные выходы и NULL для пустых измерений. Для текущей fixture Q7 известные длительности равны `7/3` суток; сравнивать с Decimal-допуском. Затем сделать хотя бы две разные длительности и частичную долю опозданий, например `1/3`, чтобы обнаруживать неверный вес, целочисленное деление и единицы времени. Q9 отдельно проверять обе средние по штату и средние по каждому способу в обоих периодах. Q10 — числа, обе знаменательные выборки и пустые группы. Исправлять текущие формулы SQL на основании R1 не требуется: ошибка здесь в regression gate.

### R2 — P2: проверка порога не различает `>=` и `>`

**Места:** `answers/q06-q10/test_fixture.py:53–64`; проверяемая граница — `q07.sql:23`.

Исходная fixture содержит один штат SP: 10 заказов всех статусов и 9 delivered. Тест проверяет пустой результат при 500 и наличие групп после замены порога на 2. Ни одна группа не находится на границе.

**Контрпример:** мутант `HAVING count(*) > min_orders` вместо текущего корректного `>=` оставит все существующие проверки успешными: 9/10 меньше 500 и больше 2. Но штат с ровно 500 заказами исчезнет, хотя организаторы требуют «не меньше 500». В малой проверке Python непосредственно сверены обе операции на всех четырёх сочетаниях численности/порога теста: результаты одинаковы.

**Минимальный fix:** на параметризованном пороге 2 создать отдельные штаты с 1, 2 и 3 заказами и проверить точный набор групп; для одной пограничной группы оставить отсутствующую дату доставки, чтобы проверить применение порога до исключений. Ключ `by7` в `:58` должен включать `customer_state`: сейчас он состоит только из population/late_basis и при расширении fixture молча перезапишет разные штаты. Исходный порог 500 оставить отдельно проверяемым. Текущий SQL уже использует правильное `>=`; исправление требуется тесту.

## Открытые политики, не SQL-bugs

1. **Q6:** организаторы просят один товар; запрос возвращает всех лидеров отдельно для двух популяций. Для итогового ответа выбрать популяцию и либо документировать все ничьи, либо добавить стабильный выбор одного товара (например, product_id) с объявленным правилом. `ORDER BY` упорядочивает ничьи, но не выбирает победителя. Дата покупки против другой даты также должна быть зафиксирована.
2. **Q7:** популяция порога, покупка/передача перевозчику как начало срока, дата/timestamp как критерий опоздания. Реализованное правило `>=500` соответствует тексту; предпочтение одной бизнес-трактовки из требований не следует.
3. **Q8:** текст результата требует текущие статусы и пустые заказы. Распределение снимка это выполняет; восстановление переходов и конверсий из него не обосновано. Вывод нулевых известных статусов можно добавить, если согласован такой формат.
4. **Q9:** год определяется покупкой, поскольку времени платежа нет; NULL даты не попадают в 2018, но остаются в `all_snapshot`. Срок в месяцах не восстановим из числа частей. Нужно выбрать период второго результата, среднюю всех типов/только карт и правило для нулевых частей. Сейчас нули включены согласно исходному значению; исключить их без решения нельзя.
5. **Q10:** группы `within_score` пересекаются; итог `sum(orders_count)` не является уникальным числом заказов. В `single_score_only` заказ с оценками 5 и 6 исключается: `score_counts` считает все известные оценки до фильтра 1–5. Это соответствует комментарию SQL; если требуется «одна допустимая оценка», фильтр надо перенести до подсчёта конфликтов и изменить описание/coverage. Оценка NULL рядом с 5 не считается вторым известным мнением.

Полезные дополнительные малые случаи для усиления fixture: два одинаковых score у одного заказа (сейчас удаление DISTINCT из Q10 тест не обнаружит), оценки `{5,6}`/`{6}`/`{NULL}`, NULL штат, NULL дата/цена у победителя Q6, повторение одной цены несколькими единицами в один день, границы года Q9. Это перечисление недостающего покрытия, а не утверждение, что нынешний SQL ошибается на этих входах.
