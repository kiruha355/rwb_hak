## Строки SQL

Все имена ниже относятся к опубликованному SQL. Деньги — исходные единицы
датасета, дни — дробные сутки. Поля `*_pct` — проценты 0–100. NULL остаётся
неизвестным/невычислимым значением, без замены нулём.

| Вопрос / представление | Поля одной строки | Ключ строки и отображение |
|---|---|---|
| Q6 `mart.q06_price_history` | `population`, `product_id`, `distinct_prices`, `units_with_unknown_price`, `purchase_date`, `price`, `units_sold` | `(population, product_id, purchase_date, price)`; дата×цена, единицы. Все лидеры с равным максимумом сохранены. Несколько цен за день нельзя усреднить в одну точку без изменения вопроса. |
| Q7 `mart.q07_delivery_by_state` | `population`, `customer_state`, `late_basis`, `orders_count`, `duration_denominator`, `avg_delivery_days`, `late_denominator`, `late_orders`, `late_pct` | `(population, customer_state, late_basis)`; SELECT ответа применяет `orders_count >= 500`. Сам view содержит также группы ниже порога. |
| Q8 `mart.q08_status_snapshot` | `order_status`, `orders_count`, `orders_pct`, `orders_without_items` | `order_status`; распределение текущих статусов и пустых заказов. Переходы и конверсию между этапами оно не измеряет. |
| Q9 `mart.q09_payments_2018_by_state` | `customer_state`, `payment_count`, `amount_denominator`, `payment_amount`, `known_payment_amount_sum`, `installments_denominator`, `avg_installments_all_types`, `credit_installments_denominator`, `avg_installments_credit_card` | `customer_state`; все платёжные записи заказов, купленных в 2018. Это не дата платежа. Два средних числа частей, не срок в месяцах. |
| Q9 `mart.q09_payment_methods` | `period`, `payment_type`, `payment_count`, `installments_denominator`, `avg_installments` | `(period, payment_type)`; окно — часть строки, нельзя смешивать окна в одной сумме. |
| Q10 `mart.q10_review_delivery` | `population`, `score_policy`, `late_basis`, `review_score`, `orders_count`, `duration_denominator`, `avg_delivery_days`, `late_denominator`, `late_orders`, `late_pct` | `(population, score_policy, late_basis, review_score)`; после выбора трёх параметров ровно пять оценок 1–5. Всего view даёт 40 строк вариантов. |
| Q10 `mart.q10_review_coverage` | `population`, `orders_count`, `orders_without_score`, `orders_with_multiple_scores`, `orders_in_multiple_valid_score_groups`, `orders_with_out_of_range_score` | `population`; диагностические причины могут пересекаться, их нельзя складывать как непересекающиеся части итога. |

Enum-поля:

- `population`: `all_statuses` / `delivered`.
- `late_basis`: `calendar_day` / `timestamp`.
- `score_policy`: `within_score` / `single_score_only`.
- `period`: `all_snapshot` / `purchase_2018`.

`population` есть только в указанных Q6/Q7/Q10 relations. В Q9 срез `delivered`
есть в CSV-исследовании, но **не реализован в этих двух SQL-представлениях**.
Не обещать UI-фильтр, который view не поддерживает.

## Примеры чтения

```sql
-- Один конкретный вариант Q7. Можно параметризовать обоими enum и порогом.
SELECT * FROM mart.q07_delivery_by_state
WHERE population = 'delivered' AND late_basis = 'calendar_day'
  AND orders_count >= 500
ORDER BY customer_state NULLS LAST;

-- Два ряда Q10 для сравнения; каждый ряд — отдельная серия на графике.
SELECT * FROM mart.q10_review_delivery
WHERE population = 'delivered' AND late_basis = 'calendar_day'
ORDER BY score_policy, review_score;

-- Отдельные окна Q9, не одна суммируемая совокупность.
SELECT * FROM mart.q09_payment_methods
ORDER BY period, payment_type NULLS LAST;
```

## Условия интерфейса и API

- Для каждой серии явно сохранять `population`, `late_basis`, `score_policy` и
  `period`, где они предусмотрены. Не суммировать строки разных вариантов.
- В Q7/Q10 средний срок и доля опозданий имеют **разные знаменатели**. Число
  заказов в группе не является автоматическим знаменателем обоих показателей.
  Не усреднять средние штатов простым средним.
- `within_score`: заказ может входить в несколько оценок. Сумма пяти counts
  не равна числу уникальных заказов. `single_score_only` исключает конфликты.
- В Q6 `units_with_unknown_price` — итог товара в популяции, повторяемый на каждой
  строке его истории. Его нельзя суммировать по датам/ценам.
- Пустая группа Q10: `orders_count = 0`, среднее и доля NULL. Неизвестный штат,
  цена или дата — отдельное неизвестное значение, не ноль и не другая группа.
- Q7/Q10 durations в обоих вариантах population вычисляются только для delivered
  с необходимыми датами; `all_statuses` расширяет counts, не делает доставку
  недоставленных измеримой. Отрицательный purchase→delivery исключён из среднего.
- Q9 `payment_amount = NULL` при неполном покрытии; известная часть остаётся в
  `known_payment_amount_sum`. Число частей не переименовывать в месяцы.
- Эти views агрегированы по всему снимку (Q9 states — фиксированное окно 2018).
  Общие фильтры приложения по категории/месяцу не поддерживаются простым фильтром
  уже агрегированных строк. Для такого сценария нужен отдельный серверный расчёт
  из detail mart/core, иначе экран должен честно оставаться в указанном scope.
  Q6 «лидер внутри выбранного периода» требует заново определить максимум,
  а не отфильтровать историю глобального победителя после расчёта.
- API должен различать отсутствие новой схемы/ошибку БД и успешный пустой ответ.
  При недоступной новой view показать недоступность раздела, а не пустые данные.
- SQL variants можно отдавать отдельным endpoint или дополнительными ключами
  существующего ответа без изменения Q1–Q5. Это предложение интеграции; такого
  HTTP-контракта пока нет, его реализует владелец API.

## Что ещё не готово

Новые запросы проверены на PG16.15: 16 синтетических заказов для поведения,
отдельные 10 — clean build/rebuild/rollback/answers/check. Прежний PG17 PASS не
используется как доказательство этих байтов. Полный Olist SQL, CSV→raw equality
этой сборки, новые реальные итоговые ответы и приложение после подключения не
проверены. CSV-experiments в `experiments/` — сравнение гипотез, не DB-ответы для
пользовательского экрана. Веб-приложение не должно выдавать их за live mart.

История категории требует сохраняемого входа изменений и проверки стабильности
старого отчёта после смены/rebuild. Адресные поля уже есть на заказе; отдельная
проверка обновления профиля и rebuild ещё нужна. Паспорта новых метрик и материалы
сдачи должны быть обновлены после интеграции определений и фактических результатов.

Для приёмки UI нужны: реальный endpoint на согласованной БД, NULL/пустая группа,
ошибка недоступной view, обе серии Q10, два окна Q9, корректные подписи и снимок
широкого/узкого экрана. Это работа следующего этапа, не текущий E2E PASS.
