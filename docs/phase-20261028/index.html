Сроки и опоздания: Q7 и Q10

Для покупателя срок ожидания начинается с покупки; для перевозчика — с получения посылки. Эти интервалы отвечают на разные вопросы. Рекомендация для обязательного ответа — покупка → вручение, в дробных сутках. Интервал перевозки можно оставить дополнительным показателем.

Настоящая строка Olist

order_id = 8563039e855156e48fccee4d611a3196, статус delivered.

Покупка17.02.2018 15:59:46
Обещанное вручение20.03.2018 00:00:00
Фактическое вручение20.03.2018 00:59:25

По календарю заказ пришёл вовремя. По точному времени он опоздал на 59 минут 25 секунд. Полночь в обещании сама по себе не доказывает обещание вручить до начала дня.

Независимые CSV-проверки Astra и Sol получили разную чувствительность к правилу. Все известные обещанные даты в этом снимке имеют время 00:00:00.

Какие заказы входят в расчёт

Предлагаемая основная совокупность — delivered. Для Q7 порог 500 применяется к числу delivered-заказов штата до исключения недостающих дат. Сам срок и доля опозданий имеют отдельные знаменатели: только заказы с нужными известными датами; отрицательный срок исключается из среднего. Отсутствующая дата не означает ноль дней или своевременность.

Альтернативы — порог по всем заказам либо только по измеримым срокам. На текущем CSV все три правила оставляют 17 штатов, но при новых данных их состав может различаться. Проверка должна включать 499/500 заказов и отсутствие даты.

Проверенная рабочая рекомендация: «delivered; покупка→вручение; опоздание по дню; порог по delivered». Вопрос об утверждении снят; исследование завершено. Варианты SQL сохраняются для разных задач и проверки чувствительности; человеческого утверждения единственного варианта нет.

Итог эксперимента: для ожидания покупателя гипотеза поддержана; время перевозки и timestamp-опоздание полезны как отдельные показатели. Все проверенные правила порога дают те же 17 штатов, поэтому выбор одного не блокирует работу. Общий фильтр «удалить любой заказ с аномалией» потерял бы 1 373 пригодных срока — пригодность нужно определять для каждой метрики. Полные проверки доставки и контрпримеры.

Какая оценка представляет заказ: Q10

Один заказ может иметь несколько отзывов. У 202 заказов в CSV встречаются разные оценки; среди delivered — у 189. Сохранение всех пар отзыв–заказ уже принято. Осталось определить, как группировать такие заказы в ответе по оценкам 1–5.

Условный пример группировки

У одного заказа есть оценки 2 и 5, срок доставки — 10 дней.

При таком правиле заказ один раз входит в каждую встреченную оценку. Числа заказов по пяти группам нельзя складывать: группы пересекаются.

Первоначальная рекомендация — DISTINCT(order_id, review_score): одна строка на заказ внутри каждой оценки. Вопрос о её принятии снят. Завершённый CSV-эксперимент сравнил пять правил: каждую оценку, только однозначную, последнюю по созданию отзыва, последнюю по ответу и минимальную.

Что изменил эксперимент

Наблюдаемая связь устойчива ко всем пяти правилам: с ростом оценки от 1 до 5 средний срок и доля опозданий последовательно уменьшаются. Максимальная разница между правилами внутри одной оценки — 0,033 дня и 0,192 процентного пункта. Это измеренный размах на текущем снимке, без придуманного порога «достаточно мало».

Разница остаётся в составе групп: 95 832 delivered-заказа имеют оценку. Первый вариант даёт 96 021 связь заказ–оценка, второй сохраняет 95 643 заказа и отдельно показывает 189 конфликтных. Оба представления полезны одновременно: одно сохраняет наблюдаемые мнения, другое проверяет связь на однозначной подвыборке. Вопрос о выборе единственного правила пока не нужен.

Платежи и рассрочка: Q9

Дата платежа в источнике отсутствует. Поэтому «2018» можно отнести к дате покупки заказа; называть это годом фактического поступления денег нельзя. Одна строка платежа остаётся отдельным наблюдением: соединение с позициями умножило бы сумму.

Два исходных card-платежа содержат 0 частей. Их нужно сохранить и показать охват; замена на 1 или NULL изменит данные и требует отдельного правила. Неизвестная сумма не становится нулём: известная часть суммы и число заполненных значений выводятся отдельно.

Статусы и окна явно именованы в SQL. Представление дополнительных рядов сохраняет смысл каждого, поэтому выбирать единственную колонку или окно только ради компактности не требуется.

Результат эксперимента: среднее число частей в покупках 2018 — 2,725449 по всем способам и 3,302485 по кредитным картам. Это два разных показателя, которые полезно показывать рядом. Оба окна разреза способов — 2018 и весь снимок — также можно сохранить, поэтому угадывать единственное прочтение «целиком» не требуется. Данные, примеры и проверки Q6/Q9.

История цен: Q6

В Olist есть цена каждой проданной единицы и дата покупки заказа. Истории изменения каталожного прайса нет. Поэтому ответ показывает наблюдаемые цены сделок: день покупки × цена → число единиц; несколько цен за день сохраняются.

CSV-лидер одинаков для двух совокупностей: 437c05a395e9e47f9762e677a7068ce7, 31 известная цена. Все статусы дают 155 единиц и 77 групп день×цена; delivered — 151 единицу и 76 групп. У товара три продавца, поэтому эти наблюдения нельзя выдавать за прайс одного продавца.

Рекомендация — delivered, как завершённые продажи. Альтернатива — все наблюдавшиеся позиции, включая заказы, которые не были вручены. При равенстве максимума запрос сохраняет всех лидеров; выбор одного товара для показа можно сделать явно, не теряя остальных из результата. Это ещё не принятое определение.

История категорий и адрес заказа

Сейчас позиция получает категорию через единственное текущее значение товара. Если заменить категорию и перестроить модель, прошлый отчёт может измениться. Простое добавление valid_from / valid_to не решает проблему: сборка удаляет и создаёт таблицы заново.

Нужен источник версий, переживающий rebuild: журнал входных изменений или версионированные входы. Начальное значение из Olist — baseline снимка; дата начала его реального действия неизвестна. Проверка A→B будет учебным изменением, а не выдуманной историей Olist.

В CSV 1 225 товаров встречаются у нескольких продавцов. Глобальное изменение категории товара затронет всех продавцов, а изменение назначения одного продавца — только его позиции. Архитектурный эксперимент ниже сохраняет оба уровня.

Результат архитектурного эксперимента

Не требуется выбирать только одну идентичность. Общая категория товара служит baseline; изменение продавца хранится как отдельное назначение для пары товар–продавец. Позиция заказа получает сохранённую ссылку на версию. Журнал и начальный снимок переживают rebuild; опубликованный выпуск отчёта закрепляет прежние привязки. Позднее исправление создаёт отдельный пересмотренный выпуск, сохраняя исходный.

Проверены два механизма хранения: неизменяемые снимки и журнал событий с сохранёнными привязками. Рекомендован журнал с baseline и контрольными снимками. 19 проверок Python-симуляции прошли: смена A→B, другой продавец, заднее число, повтор, холодное восстановление и сохранность старого выпуска. PostgreSQL DDL и модель ещё не реализованы. Архитектура, алгоритм и пределы · неисполненный DDL-план.

Адрес: индекс, город и штат уже сохранены у заказа, отдельно от личности покупателя. Полного почтового адреса в CSV нет. Нужно проверить, что два заказа одного покупателя сохраняют свою географию после изменения текущего профиля и rebuild. Само наличие разных адресов не доказывает переезд.

Проверки и принятие решений

Основные источники — требования организаторов, опубликованные SQL, локальные CSV и результаты проверок. Веб-исследования дают идеи и практики. Рекомендации post-mortem используются как основания; общими правилами автоматически не объявлены.

  1. Агенты независимо исследуют альтернативы по явным критериям, данным и различающим экспериментам. Для разных полезных вопросов можно сохранить оба показателя.
  2. Sol связывает каждый эксперимент с отдельным выводом и проверяет возражения. Равнозначная остаточная развилка получает объяснение рядом с конкретным вопросом; только затем используется ask-question.
  3. Предложение, рабочая гипотеза и явное решение пользователя сохраняют разные статусы. Снятые вопросы Q7/Q10 ответов и approvals не дали.
  4. Результат связывается с SQL, паспортом и материалами сдачи. Проверяется исполнение новых байтов и опубликованное дерево. Fixture, CSV-сверка и полный lifecycle имеют разные границы.

Ресурсы: 28.10 в 13:16 UTC dev-job preflight вернул 78: 26,74 ГиБ свободно, memory pressure 2, swap 2,71 ГиБ. Тяжёлый локальный запуск запрещён. На установленном PG16.15 прошли малые проверки: 16 синтетических заказов для Q6–Q10 и 10 для lifecycle. Временный сервер удалён; протокол и хеши входов. Полный Olist lifecycle остаётся pending.

Источники и границы

Сравнения 6 534/7 826, 202/189, 56 015/54 748 и 155/151 — результаты CSV-анализа из разбора Astra и сверки Sol. Оба отчёта прочитаны координатором; каждый автор сверил 8/8 хешей с baseline. Реальный пример заказа дополнительно извлечён координатором из локального CSV. Здесь нет новых контрольных результатов Q6–Q10 из модели.

Полный post-mortem: 50 найденных связанных тредов, полный messages-view, адресный activity с остаточными обрезками; недоступный разговор коллеги не охвачен. Его локальные файлы не объявлены опубликованными.
