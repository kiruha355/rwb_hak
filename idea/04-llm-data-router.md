# LLM-помощник: куда в модели положить новые данные

**Статус:** 💡 идея · **Дата:** 2026-10-28 · **Приоритет:** бонус (дополнение, не основа)

## Зачем
Новые данные приходят постоянно: новый источник, новая колонка, «вброс» на хакатоне.
Инженер каждый раз решает одно и то же: какое тут зерно, это факт или справочник,
с чем связать, где историчность. Помощник ускоряет это решение, но не принимает его сам.

Задевает критерии:
- **использование ИИ** (15): прозрачность, проверка результата, собственные решения;
- **реакция на вброс** (часть 25 за понимание);
- **стратегия развития**: как модель принимает новые сущности.

## Суть
LLM получает **профиль** новых данных и **каталог** текущей модели и предлагает, куда
и как их встроить. Человек проверяет и утверждает. В `core` ничего не применяется
автоматически.

## Поток
```
новый файл / новая колонка
        │
        ▼
1. Детерминированный профайлер (SQL/Python, без LLM)
   колонки, типы, доля NULL, кардинальность, кандидаты в ключ (уникальность),
   пересечение значений с существующими ключами (например, 98 % значений
   колонки X совпадают с fact_order.order_id → вероятный FK)
        │
        ▼
2. LLM: профиль + catalog.json модели (тот же, что для карты DWH)
   → предложение:
     • зерно: «одна строка = …»
     • куда: новый факт / новый справочник / атрибут существующей таблицы / SCD2
     • ключ и связи (FK)
     • правила чистки и приведения типов
     • черновик DDL + INSERT … SELECT FROM raw.…
     • самопроверки для новой таблицы
     • уверенность и альтернативы
        │
        ▼
3. Проверка: SQL выполняется в песочнице (схема sandbox), прогоняются
   предложенные проверки и проверки модели (ничего не сломалось, суммы сошлись)
        │
        ▼
4. Человек: принять / поправить / отклонить → запись в журнал решений
   (что предложил ИИ, что выбрали мы и почему)
```

## Почему это не «магия»
- Шаг 1 детерминированный: LLM получает **факты**, а не угадывает по названию колонки.
- Наружу уходят только **метаданные и агрегаты** профиля, не строки данных.
- Шаг 3 проверяет результат: предложение без пройденных проверок не показывается как готовое.
- Шаг 4 оставляет решение за человеком. Журнал решений идёт в `06-ai-usage-log.md` и в записку.

## Демо-сценарий для защиты
Берём «новый» источник: например, геолокацию по индексам (её нет в выгрузке; есть
в полном датасете Olist) или то, что придёт во вбросе. Показываем:
профиль → предложение LLM → проверки в песочнице → наше решение (возможно, с правкой).

## Зависимости
- Модель `core` и `catalog.json` (см. `03-dwh-map.md`).
- Доступ к LLM API (какой — решить), ключ хранится вне репозитория.

## Риски
- Галлюцинации ключей и связей → смягчаем профайлером и проверками.
- Время: это бонус. Не начинаем, пока не готовы модель, ответы и записка.
- Приватность: отправляем только метаданные.
