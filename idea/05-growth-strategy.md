# Стратегия развития: от хранилища для аналитиков к self-service

**Статус:** 💡 черновик · **Дата:** 2026-10-28 · **Приоритет:** обязательно (20 баллов)

Критерии оценки: развитие логической структуры · узкие места при росте ·
технологический стек · этапность и риски перехода.

## Главная мысль
Модель данных — фундамент. Всё «удобное для людей» (дашборды, чат с LLM, алерты, ML)
строится поверх неё и работает хорошо, только если фундамент правильный.
Поэтому сначала модель, потом слои удобства.

```
источники → DWH (raw → core → mart) → семантический слой (метрики на бизнес-языке)
                                              │
              ┌───────────────┬───────────────┼───────────────┬──────────────┐
           аналитики      дашборды        чат с LLM         алерты       ML-модели
           (SQL)          (руководство)   (все остальные)   (операции)   (прогнозы)
```

## Кто пользуется DWH в реальной компании
| Кто | Что делает | Что ему нужно |
|---|---|---|
| Инженеры данных | строят и поддерживают хранилище | схема, lineage, мониторинг загрузок, проверки качества |
| Аналитики | пишут SQL, исследуют, строят отчёты | чистая модель `core`, каталог данных, описание метрик |
| Data Scientists / ML | прогнозы, рекомендации | исторические данные, готовые признаки (feature store) |
| Менеджеры и руководители | принимают решения | дашборды, понятные метрики, алерты |
| Продавцы на маркетплейсе | смотрят свои продажи | личный кабинет со своей статистикой |
| Операционные сотрудники (логистика, поддержка) | ежедневные задачи | простые отчёты: «какие заказы сегодня опаздывают» |
| Внешние: инвесторы, партнёры, регуляторы | итоговые показатели | сводная отчётность |

Чем ниже по таблице, тем меньше человек разбирается в данных и тем проще для него должен быть интерфейс.

## Self-service для «людей не из аналитики» (демократизация данных)
1. **Семантический слой.** Метрики описаны один раз на бизнес-языке: «Выручка = …», «Активный покупатель = …». Человек выбирает «выручка по месяцам» мышкой, без SQL. Инструменты: dbt Semantic Layer / MetricFlow, Cube, LookML.
2. **Каталог данных.** «Википедия» по данным: что значит таблица и метрика, кто владелец, насколько свежая. Инструменты: DataHub, OpenMetadata. Наш `catalog.json` (`03-dwh-map.md`) — зародыш этого.
3. **Дашборды под роли.** Директору — 5 главных цифр, логисту — опоздания, продавцу — его продажи (см. `02-dashboard.md`).
4. **Вопросы на естественном языке через LLM.** «Сколько заработали в мае на электронике?» → SQL поверх модели → цифра с пояснением. Здесь чистая модель критична: на сырых данных LLM ошибается так же, как люди (см. `07-llm-chat-with-data.md`).
5. **Алерты.** Не ждать, пока кто-то откроет дашборд: «продажи в штате SP упали на 30 % за неделю».

## Развитие логической структуры (черновик)
**Новые сущности:**
- геолокация (индекс → координаты), если подключить полный датасет;
- логистические партнёры и отправления (shipment как отдельный факт: у заказа с несколькими продавцами несколько отгрузок);
- комиссии и тарифы → маржа и прибыль;
- возвраты и обращения в поддержку;
- маркетинг: источники трафика, промокоды (ваучеры уже видны в платежах);
- события воронки (просмотр → корзина → заказ) — тогда «от корзины» станет буквальным;
- статусы заказа как история событий (`fact_order_status_event`), а не одно последнее значение.

**Где понадобится историчность (SCD2 / снимки):**
- адрес покупателя (уже сейчас меняется у 250 человек);
- карточка товара: категория, цена, габариты;
- продавец: город, статус, тариф;
- статус заказа (сейчас видно только финальное состояние).

## Узкие места при росте (черновик)
- Полная пересборка `core` из `raw` на каждый запуск → нужна **инкрементальная загрузка** (по `_loaded_at` или водяным знакам, `MERGE`/upsert).
- Тяжёлые агрегаты дашборда по сырым фактам → **предагрегированные витрины** в `mart`, материализованные представления.
- `count(distinct customer)` и медианы на больших объёмах → приближённые алгоритмы (HyperLogLog) или предрасчёт.
- Один PostgreSQL для загрузки и для чтения → конкуренция за ресурсы; реплика для чтения.
- Ручной запуск скриптов → оркестрация и мониторинг (Airflow / Dagster, проверки качества: dbt tests / Great Expectations).

## Технологический стек (черновик, проверить цифры)
| Этап | Объём (ориентир) | Стек | Почему |
|---|---|---|---|
| Сейчас | ≤ десятков ГБ, миллионы строк | PostgreSQL + SQL-скрипты | хватает с запасом, просто объяснить |
| Рост | сотни ГБ, сотни млн строк | PostgreSQL + партиционирование по дате, индексы, матвью; dbt для трансформаций и тестов; Airflow / Dagster | дешево, без смены СУБД |
| Аналитический масштаб | ТБ, миллиарды строк, много одновременных аналитиков | колоночная OLAP: **ClickHouse** (self-hosted, быстрые агрегаты) или облачные Snowflake / BigQuery; S3 + Iceberg как lakehouse | колоночное хранение и сжатие для агрегатов; OLTP-СУБД здесь упирается в скан |
| Поверх | — | семантический слой (dbt SL / Cube), BI (Superset / Metabase / Datalens), каталог (OpenMetadata), LLM-чат | self-service |

Ориентиры по объёмам — **гипотеза**, нужно подкрепить источниками или бенчмарками.

## Этапность и риски перехода (черновик)
1. Стабилизировать модель и тесты на PostgreSQL. Риск — нет; база для всего.
2. dbt поверх PostgreSQL: те же SQL, плюс тесты, документация, lineage. Риск низкий.
3. Инкрементальная загрузка и оркестрация. Риск: расхождение с полной пересборкой → еженедельная полная сверка.
4. Перенос витрин `mart` в ClickHouse, `core` пока остаётся в PostgreSQL. Риск: два источника правды → `mart` строго производный, сверки сумм.
5. Семантический слой, каталог, LLM-чат, алерты. Риск: LLM отвечает неверно → только поверх семантического слоя, с показом SQL и источника.
