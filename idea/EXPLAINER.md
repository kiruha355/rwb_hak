# Объяснялка: кейс «Модель маркетплейса» простыми словами

**Версия:** итоговая, по сводке команды `docs/idea-synthesis.md` v2 в `main`
(коммит `1939068`). Рекомендации сводки здесь считаются **принятыми решениями** —
это то, что мы показываем на защите.

Для всех в команде, кто хочет за 15–20 минут понять, что мы строим, почему
именно так и что у нас спросят. Без знания SQL читаются разделы 1–3, 8, 10 и 12;
остальное — для тех, кто пишет модель.

Все цифры проверены запросами к базе. Наглядный макет того же самого —
`idea/prototype.html`.

---

## 1. Суть за одну минуту

- Маркетплейс **Capibara** — на деле реальные данные бразильского Olist
  (09.2016–10.2018, ~100 тыс. заказов, 550 759 строк в 8 таблицах).
- Данные лежат «как пришли» (схема `raw`): грязные и несогласованные.
  Каждый аналитик считает по-своему, и цифры не сходятся.
- **Наша задача** — построить **модель** (схема `core`): аккуратные таблицы,
  где все правила («что такое выручка», «кто такой покупатель») записаны
  один раз. Ответы и дашборд считаются **только из модели** (схема `mart`).
- Сдаём: скрипт сборки одной командой, ответы на 10 вопросов, записку о
  решениях (≤ ½ стр.), описание дашборда, стратегию развития, журнал ИИ.
  Плюс **презентация**: по стенограмме встречи её тоже оценивают.
- **Больше всего баллов** дают качество модели и умение объяснить своё
  решение на нашем коде.

## 2. Как устроен бизнес и данные

```
 Покупатель ──оформляет──▶ Заказ ──содержит──▶ Позиции (товар + продавец)
                             │                     │
                             ├──оплачивается──▶ Платежи (1..n, рассрочка)
                             │                     │
                             └──получает──▶ Отзыв   └──▶ Товар ──▶ Категория
                                                    └──▶ Продавец
```

Жизнь заказа: `оформлен → оплата подтверждена → передан перевозчику → вручён`
плюс **обещанная дата** доставки и крайний срок отгрузки у продавца.

| Таблица `raw` | Одна строка = | Строк |
|---|---|---|
| orders | один заказ (статус + все даты) | 99 441 |
| order_items | одна **единица товара** в заказе | 112 650 |
| order_payments | одна платёжная строка заказа | 103 886 |
| order_reviews | связь «отзыв — заказ» (`review_id` повторяется!) | 99 224 |
| customers | покупатель **в конкретном заказе** | 99 441 |
| products | карточка товара | 32 951 |
| sellers | продавец | 3 095 |
| product_category_translation | перевод категории | 71 |

**Чего в данных нет** (это важно для честных выводов): выкупа и возвратов
(`delivered` — это «вручён», а не «выкуплен»), корзины, комиссий и
себестоимости, координат (только штат и начало индекса), часового пояса.

## 3. Почему аналитики получают разные цифры

Простой вопрос «какая у нас выручка?» — разумные способы дают разброс в миллионы:

| Способ посчитать | Результат |
|---|---|
| цены товаров, только доставленные, 09.2016–08.2018 | **13 221 498.11** ← правильный ответ |
| то же, но с доставкой | 15 424 463.65 |
| сумма платежей по доставленным | 15 422 461.77 |
| цены + доставка, все статусы, весь период | 15 848 243.14 |
| все платежи, соединённые с позициями | 20 308 134.71 |
| правильный способ, но с JOIN на отзывы | 13 168 332.11 |

Последний — самый коварный: у 547 заказов несколько отзывов, они **удваивают**
суммы, а 768 заказов без отзыва **пропадают**. Ошибки почти гасят друг друга,
итог отличается всего на 53 тыс. — никто не заметит.

Живой пример: заказ `f41397c4…` — 3 позиции от 2 продавцов, 1 платёж на 100.70.
Наивное «заказ × позиции × платежи» даёт 302.10, а каждый продавец
«зарабатывает» по 100.70 вместо 11.55 и 41.78.

**Вывод:** проблема не в SQL, а в том, что правила не записаны в одном месте.
Это и есть то, что мы чиним.

## 4. Пять понятий, без которых не объяснить модель

**Зерно** — что значит одна строка таблицы, одной фразой: «одна строка = один
заказ». Средний чек считается на уровне **заказа**, выручка продавца — на
уровне **позиции**. Перепутаешь уровень — получишь неверный чек.

**Ключ** — колонки, которые однозначно определяют строку. Объявляем в базе
(`PRIMARY KEY`) — база сама не пустит дубль. Связи (`FOREIGN KEY`) не пустят
«сироту» и **незнакомый статус**.

**Факт и справочник (измерение).** Факт — событие с числами (заказ, позиция,
платёж, отзыв). Справочник — «кто/что/когда» (покупатель, товар, продавец,
категория, дата, статус). Вместе — «звезда»; несколько фактов с общими
справочниками — «созвездие». В критериях жюри прямо названо «разделение на
факты и измерения».

**Аддитивность.** Выручку можно складывать по месяцам, штатам, категориям.
**Средний чек, доли, среднюю оценку, число уникальных покупателей, медиану** —
нельзя: пересчитываем из числителя и знаменателя.

**NULL ≠ 0.** «Неизвестно», «ноль» и «строки нет» — три разных состояния.
У заказа без позиций выручка **неизвестна** (NULL), а позиций в нём **0**.
Подменять NULL нулём в модели нельзя — иначе средние врут.

## 5. Ловушки в данных и что мы с ними делаем

| Ловушка | Что будет, если не заметить | Решение |
|---|---|---|
| `customer_id` новый в каждом заказе | 99 441 «покупатель», повторных 0 % | покупатель = `customer_unique_id` |
| У 250 человек разные индексы в разных заказах | «один человек в двух городах» (это может быть другой адрес доставки, а не переезд) | адрес — **снимок на заказе**, без истории |
| `review_id` не уникален (789 общих), у 547 заказов >1 отзыва | суммы удваиваются при JOIN | ключ отзыва = (`review_id`, `order_id`); содержание у повторов одинаковое, все 789 — у одного покупателя |
| 775 заказов без позиций | INNER JOIN молча их теряет | остаются в `fact_order`: суммы NULL, позиций 0 |
| 610 товаров без категории (1 537 доставленных позиций) | сумма по категориям меньше общей | член справочника `unknown` |
| 2 категории без перевода | пустое английское имя | английское = португальскому + флаг `is_translated = false` («нет перевода» ≠ «нет категории») |
| Ноябрь 2016 — ноль заказов | 23 месяца вместо 24 | непрерывный календарь `dim_date` + проверка непрерывности |
| Выручка без доставки, чек — с доставкой | путаница | три величины с разными именами: `item_revenue`, `order_gmv`, `payment_amount` |
| Платежи ≠ сумме позиций | «какая сумма правильная?» | выручка — по позициям; расхождение показываем отдельно (см. ниже) |
| Даты не по порядку: 166 переданы перевозчику раньше покупки, 23 вручены раньше передачи, 1 359 переданы раньше подтверждения оплаты, 6 недоставленных с датой вручения | неверные длительности этапов | **флаг на каждый тип аномалии**; заказ выпадает только из метрик на нарушенной паре дат. Вручения раньше покупки нет ни разу, поэтому `delivery_days` и `is_late` считаем по всем |
| Обещанная дата всегда в полночь | по времени опоздавших 8,1 %, по дате 6,8 % | `is_late` сравнивает **даты** |
| 14 доставленных без `order_approved_at` | «не оплачены» | неверно: платёж есть у всех 14, нет только отметки подтверждения |
| Грязные города продавцов (`sp / sp`, email, цифры) | «разные» города | `city_raw` + `city_clean` |
| Индексы из 4 цифр (потерян ведущий ноль?) | разные индексы одного места | `zip_prefix_raw` как есть + `zip_prefix` (5 знаков) |
| Платежи `not_defined`, нулевые, 0 частей рассрочки | странные способы оплаты | оставляем с флагами |

**Расхождение платежей — два числа, не путать.** Среди 98 665 заказов, где есть
и позиции, и платежи: суммы не совпадают точно у **639** (Σ −1 819.51); с
допуском 1 копейка — у **366** (Σ −1 818.84). Пара «366 / −1 819.51» из старых
документов смешивает два условия. Причины расхождений данные не показывают —
так и пишем.

Принцип: **грязь не удаляем, а помечаем.** Всё найденное — в журнал
`core.data_issues` с кодом и примерами.

## 6. Модель core (итоговая)

**Форма — звезда/созвездие** (а не «нормализованный core + представления»):
жюри прямо оценивает «разделение на факты и измерения», сохранность данных у
обоих вариантов одинаковая. **Ключи натуральные** (как в источнике) — проще
объяснять и сверять.

```
                         dim_date
                            │
  dim_customer ─── fact_order ─── dim_order_status (is_revenue)
                     │   │   │
           fact_payment  │  fact_review
                         │
                  fact_order_item ─── dim_product ─── dim_category
                         │
                     dim_seller
```

**Справочники**

| Таблица | Одна строка = | Ключ | Что решает |
|---|---|---|---|
| `dim_date` | день (2016-09-01 … 2018-12-31) | дата | пустой ноябрь 2016; обещанные даты до 12.11.2018 |
| `dim_order_status` | статус (8 шт.) | `order_status` | **правило выручки в одном месте**; незнакомый статус не пройдёт |
| `dim_customer` | реальный покупатель | `customer_unique_id` | 96 096 человек; первая покупка, число заказов, повторный ли |
| `dim_seller` | продавец | `seller_id` | очищенный город рядом с исходным |
| `dim_category` | категория | PT-имя или `unknown` | 74 члена; флаги `is_translated`, `is_unknown` |
| `dim_product` | товар | `product_id` | категория обязательна; `lenght` → `length`; флаг корректного веса |

**Факты**

| Таблица | Одна строка = | Ключ | Главные поля |
|---|---|---|---|
| `fact_order` | заказ (накопительный снимок всех этапов) | `order_id` | покупатель, адрес-снимок, статус, 5 дат; `lines_count`, `units_count`, `sellers_count`; `item_revenue`, `freight_amount`, `order_gmv`, `payment_amount`, `payment_coverage`, `payment_diff`, `has_payment_mismatch`; `delivery_days`, `is_late`, `days_late`, `is_handover_late`; флаги аномалий; `customer_order_seq`; `review_avg`, `review_score_latest`, `review_count` |
| `fact_order_item` | единица товара в заказе | (`order_id`, `order_item_id`) | товар, продавец, `price`, `freight_value`, срок отгрузки |
| `fact_payment` | платёжная строка | (`order_id`, `payment_sequential`) | тип, части рассрочки, сумма, флаги нулевых и `not_defined` |
| `fact_review` | связь «отзыв — заказ» | (`review_id`, `order_id`) | оценка 1–5, текст, даты, последний ли для заказа |

Важно про сборку `fact_order`: каждая «дочерняя» таблица (позиции, платежи,
отзывы) **сначала сводится к уровню заказа отдельно**, и только потом
соединяется с заказом. Так строки не размножаются.

**Служебные:** `core.data_issues` (аномалии с кодом и примерами),
`core.check_results` (результаты самопроверок).

**mart (витрины для аналитиков, всё — представления):**
`metric_definitions` (паспорта метрик, единственная таблица), широкие
`v_orders` и `v_order_items` для новых вопросов, `v_review`,
`v_payment_reconciliation`, ответы `q01`…`q10`, оценки `seller_scorecard`
и `state_scorecard`.

**Паспорт метрики** — для каждой метрики записано: формула, уровень, какие
статусы, по какой дате и в каком окне, знаменатель, что с пропусками, по
каким срезам можно складывать, единицы. Из паспортов собирается таблица
показателей дашборда — формулы не расходятся.

## 7. Как собирается и как проверяется

Одна команда (`make build check control`) на «чистой базе» — `raw` загружен,
`core` и `mart` пусты:

```
model/build.sql — одна транзакция (psql -X -1 -v ON_ERROR_STOP=1)
  00_schemas    пересоздать только core и mart (raw не трогаем)
  05_typecheck  формат денег и дат в raw; мусор → ошибка с примером
  10_dims       справочники
  20_facts      факты (дети сводятся к заказу отдельно)
  30_quality    журнал аномалий data_issues
  40_mart       паспорта метрик, широкие витрины, оценки
  50_answers    mart.q01 … q10
  90_checks     самопроверки → check_results; не сошлось → RAISE, откат всего
```

**Что проверяют самопроверки:**
- **баланс** raw ↔ core: множества ключей совпадают в обе стороны, кратности
  и суммы каждого денежного поля равны («вошло = перенесено + учтённые
  исключения»);
- ключи уникальны, внешние ключи без NULL, календарь без дыр;
- покрытие денег по группам (есть и позиции, и платежи / только одно / ничего);
- содержание повторяющихся отзывов одинаковое (если нет — предупреждение).

**Контрольные цифры** `tasks.md` — отдельный тест (`make control`), чтобы после
вброса осознанно выбрать новые ожидаемые значения. **Повторная сборка**
сравнивается с первой (`make rebuild-check`). **Манифест входа** —
SHA-256 исходных CSV и число строк.

Если сборка упала — пользователь никогда не увидит «половину модели»:
транзакция откатывается целиком, текст ошибки перечисляет упавшие проверки.

## 8. Ответы на вопросы: итоговые определения

| Вопрос | Как считаем | Что показываем | Контроль |
|---|---|---|---|
| 1. Выручка и заказы по месяцам | Σ `price`, статусы с `is_revenue`, месяц по дате оформления, месяцы из календаря | месяц, **две колонки заказов**: оформлено (99 421 за окно) и доставлено (96 478), выручка | 24 строки, ноябрь 2016 = 0, Σ **13 221 498.11** ✅ |
| 2. Топ-10 продавцов | Σ `price` его позиций | город, штат; заказов доставлено (у топ-1: 1 124), единиц (1 148) + колонка «заказов всех статусов» (1 132) | топ-1 **226 987.93** ✅; топ-10 одинаков при обеих трактовках |
| 3. Средний чек | среднее по доставленным **заказам** от `order_gmv` (товары + доставка) | чек + **три меры**: исходных строк 1.142, единиц 1.142, групп «товар × продавец» 1.039 | **159.88** ✅ (159.875) |
| 4. Покупатели | уникальные `customer_unique_id` по **всему снимку**, все статусы | всего, **вернулись (абсолютное число)**, доля | **96 096**, вернулись **2 997**, **3,12 %** ✅ |
| 5. Категории | выручка как в Q1 по категориям, `unknown` включена | категория, выручка, доля | **74**, топ `health_beauty` **1 233 131.72**, Σ = общей ✅ |

**Окна:** период задан только в Q1. Q2–Q5 — весь снимок (на Q2 и Q5 это не
влияет — доставленных вне окна нет; контроль Q4 совпадает именно со всем
снимком: в окне вышло бы 3,11 %). Это записано в паспортах метрик.

**Почему чек — по позициям, а не по платежам:** контроль сам выбирает
формулу. По позициям с доставкой — 159.875 → **159.88**, по платежам —
159.856 → 159.86.

**Почему три меры «строк» в Q3:** задание говорит «одна строка — один товар
одного продавца в заказе», но в данных у 7 088 пар товар повторяется
несколькими строками, то есть строка — это единица. Задание читается двумя
способами, поэтому даём все меры с именами, а не подменяем одну другой.

**Сейчас контроль сходится на запросах к `raw`. Сдавать — из `core`/`mart`,
и это ещё предстоит проверить на собранной модели.**

## 9. Принятые решения (что выбрали и от чего отказались)

| # | Решение | От чего отказались | Почему |
|---|---|---|---|
| 1 | Звезда с детальным зерном + широкие витрины | нормализованный core | критерий «факты и измерения»; сохранность одинаковая |
| 2 | Правило выручки — `dim_order_status.is_revenue` | фильтр в каждом запросе; глобальный фильтр delivered в core | вброс «считайте shipped» — одна строка; отмены и покупатели не теряются |
| 3 | Покупатель = `customer_unique_id`; адрес — снимок на заказе | SCD2 для адреса | разные индексы не доказывают переезд; историю из снимка не восстановить |
| 4 | `item_revenue`, `order_gmv`, `payment_amount` — три имени | одна «сумма» | задание само считает выручку и чек по-разному |
| 5 | Отзывы: факт на паре; `v_review` — производный | сущность отзыва + мост как основа | при расхождении содержания на вбросе пара ничего не теряет |
| 6 | Оценка заказа: храним и среднюю, и последнюю | одна «правильная» | «последняя = актуальное мнение» данные не доказывают; на выводы выбор не влияет (разница ≤ 0,06 п.п.) |
| 7 | Флаги аномалий по типам, исключение по метрике | один общий флаг и исключение из всего | общий флаг ничего не даёт: на `is_late` влияет 2 заказа из 6 534 |
| 8 | NULL в core, 0 в витринах только там, где он доказан | `COALESCE(…, 0)` везде | NULL ≠ 0, иначе средние врут |
| 9 | Сборка одной транзакцией + RAISE | проверки «по желанию» | никто не увидит половину модели |
| 10 | Натуральные ключи | суррогатные | проще объяснить и сверить; суррогаты — в стратегию |
| 11 | Платежи и оценки на уровне заказа | «распределить» по продавцам | правило распределения пришлось бы выдумать |
| 12 | Отказ: TLA+, анимация-таймлапс, Google Maps/Drive, оценки покупателей, LLM-маршрутизатор как приложение | — | не дают баллов, дорого или противоречат определению выручки |

## 10. Дашборд «От корзины до выкупа: выполнение и сервис»

**Для кого:** операционный директор, логистика, категорийные менеджеры.
**Решения:** каким продавцам ужесточить сроки, где разбираться с доставкой,
какие категории проседают по оценкам.

**Шапка — KPI продаж:** выручка, заказы, средний чек.
**Главный сюжет — «Цена опоздания»** (опоздание = вручили позже обещанной **даты**):

| Доставка | Доля заказов | Средняя оценка | Доля оценок 1–2 |
|---|---|---|---|
| вовремя | 93,2 % | 4.29 | 9,2 % |
| с опозданием | 6,8 % | 2.27 | 62,4 % |

Опоздание стоит около двух звёзд. Дальше разбивка: из 6 534 опоздавших
заказов **1 814 (27,8 %)** переданы перевозчику позже срока продавца; в
остальных **72 % задержка возникла после передачи**. Говорим именно так —
**без слова «вина»**: кто виноват, данные не доказывают.

**Правила показа:**
- у каждого показателя — формула, уровень, источник и **можно ли складывать**
  (из паспортов метрик);
- рядом с каждой долей — **n и знаменатель**; малые выборки помечены
  (оценки продавцов — от 30 оценённых заказов + сглаживание к средней);
- незрелые периоды (хвост 09–10.2018: 20 заказов, ни одного доставленного)
  — «нет данных», а не 0;
- аннотации: пик 24.11.2017 (Black Friday), пустой ноябрь 2016.

**Границы (что дашборд не показывает):** «delivered ≠ выкуп»; нет корзины,
возвратов, комиссий и маржи; карта — только по штатам.

**Не складываются:** средний чек, доля опозданий, средняя оценка, уникальные
покупатели, медиана дней доставки, доли категорий.

**Прототип:** после готовых ответов — Streamlit поверх `mart`, 3 экрана
(организаторы сами приводили Streamlit как пример). Макет —
`idea/prototype.html`.

## 11. Стратегия — коротко

- **Каркас:** модель — фундамент; поверх неё слои удобства: витрины,
  каталог и паспорта метрик, дашборды под роли, ИИ поверх модели, алерты.
- **Новые сущности** — только с названным источником: геолокация (9-й файл
  полного датасета Olist), воронка лидов продавцов, отгрузки, история статусов,
  комиссии, возвраты.
- **Историчность:** SCD2 там, где источник даёт изменения; из текущего
  снимка историю **не восстанавливаем**.
- **Узкие места:** полная пересборка, тяжёлые distinct и медианы, одна база
  на загрузку и чтение, ручной запуск.
- **Стек:** сначала PostgreSQL; переход дальше — **по измеренным триггерам**
  (время ответа p95, окно загрузки, число одновременных пользователей), а не
  по «порогу в N миллионов строк» — такие пороги без замеров выдуманы.
- **Этапы:** у каждого — триггер, проверка паритета со старой системой и откат.
- **Инкремент:** нужен курсор изменений **источника**; наше `_loaded_at` —
  время нашей загрузки, курсором оно не является.
- **Версия данных:** закрепить ref Olist вместо ветки `master`.

## 12. Что спросят на защите (и как отвечать)

- **«Почему такой ключ у отзывов?»** — `review_id` не уникален: 789 отзывов
  связаны с несколькими заказами. Уникальна только пара отзыв + заказ.
- **«Как убедились, что ничего не потеряли?»** — самопроверки баланса: ключи
  raw и core совпадают в обе стороны, суммы каждого денежного поля равны;
  иначе сборка падает целиком.
- **«Что будет, если выручкой станут и shipped?»** — одна строка в
  `dim_order_status`, пересборка, контрольный тест покажет новые цифры.
- **«Что будет, если придёт новый статус?»** — внешний ключ не пустит его
  молча, сборка упадёт с понятной ошибкой.
- **«Почему чек 159.88?»** — уровень заказа, товары + доставка, доставленные.
  По платежам вышло бы 159.86 — контроль различает.
- **«А 123.75 из задания?»** — ни одним из 8 способов не воспроизводится;
  наша средняя цена позиции — 119.98; вопрос задан организаторам.
- **«Почему 96 096, а не 99 441?»** — `customer_id` выдаётся на каждый заказ,
  человек — `customer_unique_id`.
- **«Почему месяц с нулём?»** — месяцы из календаря, не из данных.
- **«Кто виноват в опозданиях?»** — данные этого не доказывают; знаем только,
  что в 72 % опозданий передача перевозчику была в срок продавца.
- **«Что с грязными данными?»** — не удаляем: флаги и журнал `data_issues`.
- **«Где помогал ИИ и как проверяли?»** — журнал ИИ: что предложил, чем
  проверили (SQL-запросы + независимый CSV-срез), что решили сами. Несколько
  выводов ИИ мы **опровергли** проверкой — это тоже в журнале.

Критический путь: совещание → сборка → ответы → вброс → презентация
(≈ 7–9 часов). Документы не ждут кода — имена колонок уже зафиксированы.

**Регламент на вброс (≤ 30 минут до первого ответа):** скопировать новый
`tasks.md` → для каждого вопроса записать уровень, популяцию, окно,
знаменатель → при необходимости добавить поле в `core` и проверку →
`mart.qNN` + `answers/qNN.sql` → `make build check control` (старые ответы
не должны измениться без причины) → запись в журнал решений и ИИ.

## 15. Словарь

| Термин | Простыми словами |
|---|---|
| raw / core / mart | как пришло / наша модель / витрины и ответы для аналитиков |
| зерно | что значит одна строка таблицы |
| PK / FK | ключ строки / ссылка на строку другой таблицы |
| факт / справочник (измерение) | событие с числами / «кто, что, когда» |
| звезда / созвездие | факт со справочниками вокруг / несколько фактов с общими справочниками |
| накопительный снимок | одна строка на заказ со всеми этапами его жизни |
| аддитивная метрика | можно складывать по срезам (выручка); неаддитивная — нет (средний чек, доли) |
| паспорт метрики | формула, уровень, статусы, окно, знаменатель, пропуски, срезы |
| `item_revenue` / `order_gmv` / `payment_amount` | товары без доставки / товары + доставка / сумма платежей |
| размножение строк (fanout) | JOIN двух «один-ко-многим» по заказу дублирует суммы |
| NULL | «неизвестно» — не то же самое, что 0 |
| SCD2 | хранение истории изменений (был адрес такой, стал такой) |
| самопроверка | запрос в конце сборки, который роняет её, если цифры не сошлись |
| вброс | новое требование или данные посреди хакатона |
| MCP | способ дать ИИ-ассистенту доступ к нашим метрикам только на чтение |
