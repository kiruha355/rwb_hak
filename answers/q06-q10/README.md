Скопированный в основном репозитории файл организаторов на этом коммите содержит только Q1–Q5; эту общую копию здесь не меняем.

Запросы только читают построенную модель, ничего не создают и не меняют. Запускать по одному в `psql` на согласованной базе после успешной сборки модели, например `psql -X -v ON_ERROR_STOP=1 -f answers/q06-q10/q06.sql`. `q09.sql` возвращает два результата; `q10_coverage.sql` — отдельная диагностика охвата. В эту ветку SQL сборки и общие файлы сдачи не включены: владелец интеграции должен выбрать варианты после уточнений и подключить нужные запросы. Значений для полного Olist здесь нет: ответы не выполнены на полном наборе данных.

| Вопрос | Что считается и какие варианты доступны |
|---|---|
| Q6 | Максимум числа разных **не-NULL** цен на товар, отдельно для всех статусов и `delivered`; все товары с одинаковым максимумом сохраняются. Дата — дата покупки заказа; строка позиции — единица. NULL цены и даты остаются отдельными группами, число единиц с NULL ценой показано отдельно. Если известной цены нет ни у одного товара, строк победителей нет. |
| Q7 | Штат адреса **заказа**, включая неизвестный штат отдельной группой. Порог 500 применяется к числу заказов соответствующей популяции, до исключения отсутствующих дат; `min_orders` обратимо меняется в CTE. Отдельно все статусы и `delivered`. В обеих популяциях время и опоздание определяет существующая витрина только для `delivered` с необходимыми датами; отрицательная длительность исключается, другие нарушения хронологии сами по себе не исключают её. Время — дробные сутки от покупки до вручения, опоздание — две версии: сравнение дат или полных timestamp. Число годных значений выведено отдельно для каждого показателя. |
| Q8 | Один текущий статус на заказ; процент от всех заказов снимка, число заказов без позиций отдельно. Это распределение снимка, не история переходов статусов. |
| Q9 | В отсутствие времени платежа 2018 определяется по времени **покупки** заказа. Первая таблица — штат и платежи этого окна; вторая — способы оплаты по двум периодам: покупки 2018 и весь снимок. Один платёж — одна строка, без умножения на позиции. `payment_amount` равен NULL при хотя бы одной неизвестной сумме, известная частичная сумма и её покрытие показаны отдельно. Рассрочка — среднее исходного числа частей на платёж, не срок в месяцах и не число уникальных заказов; в разрезе штата отдельно приведена средняя по всем типам и по `credit_card`. |
| Q10 | Все статусы и только `delivered`; пять оценок и оба варианта опоздания. `within_score` учитывает заказ один раз в каждой оценке, которая ему встречается, поэтому группы могут пересекаться; `single_score_only` исключает заказ с несколькими различными известными оценками. Длительность и опоздание имеют те же условия и отдельные знаменатели, что в Q7. `q10_coverage.sql` показывает отсутствующие, конфликтующие и выходящие за 1–5 оценки. |

Отсутствующая дата или сумма не становится нулём; деление на пустой знаменатель возвращает NULL. Нет оснований трактовать наблюдаемую связь оценки и доставки как причинную. В данных нет полного журнала статусов, даты платежа, единицы времени между платежами или доказательства выкупа.

## Открытые вопросы для команды и организаторов

1. Q6: считать все наблюдавшиеся позиции или только `delivered`; как выбрать один товар при равенстве и какой момент считать датой цены? Нужны ли цены без известного значения в истории?
2. Q7: порог 500 относится ко всем заказам штата, доставленным или заказам с известной длительностью? Доставка начинается с покупки или передачи перевозчику? Опоздание сравнивается по датам или по timestamp?
3. Q8: подтверждается ли распределение текущих статусов как смысл слова «воронка»? Переходы по стадиям из снимка восстановить нельзя.
4. Q9: «за 2018 год» относится и к разрезу способов оплаты или только к штатам? Как обрабатывать отсутствие даты платежа? Среднее число частей считать для всех платежей, только кредитных карт или других типов тоже? Исходное число частей не задаёт срок в месяцах.
5. Q10: какой статусный состав использовать и как учитывать заказы с несколькими оценками? Требуется ли дополнительно исключать оценки вне 1–5 или иные нарушения хронологии? Определения длительности и опоздания — как в Q7?

Ни один из приведённых вариантов не обозначает принятое человеком решение.
