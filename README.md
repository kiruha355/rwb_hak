# Capibara: модель данных Olist

Решение кейса RWB «Модель маркетплейса: от корзины до выкупа» на открытом датасете Olist: **8 CSV, 550 759 строк**, Бразилия, сентябрь 2016 — октябрь 2018. Проект включает модель PostgreSQL, воспроизводимую сборку, SQL для десяти вопросов и дашборд о выполнении заказов, продажах и качестве сервиса. Исходный `raw` сохраняется, расчёты выполняются в `core` и `mart`.

## Особенности решения

| Решение | Что оно даёт аналитику |
|---|---|
| **Раздельные факты заказа, позиции, платежа и отзыва** | Можно считать чек по заказам, продажи по позициям и рассрочку по платежам. Независимая агрегация дочерних таблиц предотвращает размножение денег при JOIN. |
| **Устойчивая личность покупателя и адрес заказа** | `customer_unique_id` связывает повторные покупки; адресный контекст относится к конкретному заказу. Новая география покупателя не подменяет адрес предыдущего заказа. |
| **Сохраняемый источник истории категорий** | Общая категория товара и назначение продавца сосуществуют. Позиции закреплены за версиями; rebuild сохраняет исходный выпуск, а позднее исправление оформляется отдельным restatement. |
| **Неизвестные значения и аномалии остаются видимыми** | Отсутствие строки, NULL и измеренный ноль различаются. Непригодная дата исключается только из затронутой метрики; неизвестная категория не теряет продажу. |
| **Отдельные определения денег и спорных показателей** | Выручка товаров, стоимость заказа с доставкой и сумма платёжных записей имеют разные имена. Для оценок, опозданий и окон сохранены подписанные варианты с собственными знаменателями. |
| **Атомарная сборка с проверками** | Сбой обязательной проверки откатывает перестроение. Проверки сохранности и связей отделены от контрольных чисел конкретного набора, а повторная сборка проверяется отдельно. |
| **Проверки с контрпримерами и намеренными ошибками** | Проверяем не только совпадение результата: тесты должны замечать неверный JOIN, пропущенную границу порога, неверный знаменатель и потерянные данные. Ниже указано, какие проверки выполнены и на каком входе. |
| **Общие SQL-определения для ответов и интерфейса** | API читает готовые mart-представления. Дашборд показывает их варианты и покрытие, сохраняя NULL и причины недоступности данных. |

### Пример: почему нужны раздельные факты

В [реальном CSV-заказе](docs/submission/order-example.json) одна позиция за **29,99**, доставка **8,72** и три платёжные записи на общую сумму **38,71**. Если соединить позицию с платежами и сложить цену, получится **89,97**: одна цена повторится трижды. Поэтому каждый дочерний факт сначала агрегируется до нужного уровня, затем результаты соединяются. Это пример из исходного CSV, а не результат нового полного прогона core.

## Модель данных

| Факт | Одна строка | Ключ |
|---|---|---|
| `fact_order` | Заказ, включая заказы без позиций, платежей или отзывов | `order_id` |
| `fact_order_item` | Одна наблюдаемая единица товара в заказе | `(order_id, order_item_id)` |
| `fact_payment` | Одна платёжная запись | `(order_id, payment_sequential)` |
| `fact_review` | Связь отзыва с заказом и её исходные поля | `(review_id, order_id)` |

Общие справочники задают покупателя, контекст заказа, продавца, товар, категорию, календарь и статус. Непрерывный календарь сохраняет пустой ноябрь 2016; правило выручки хранится в справочнике статусов. Известная категория без перевода отличается от отсутствующей категории.

История хранится в сохраняемом `history`, а `core` и `mart` служат проекциями выбранного выпуска. Исходный снимок не содержит дат смены категорий: baseline помечается как снимок с неизвестным началом действия. Реализация хранит новые явно поступившие события, не восстанавливает выдуманную историю Olist. [Контракт модели](model/CONTRACT.md) · [История, выпуски и восстановление](model/history/README.md).

### Правила основных метрик

- **Товарная выручка:** `sum(price)` по подходящим статусам; для принятого правила — delivered, без доставки.
- **Средний чек:** среднее по delivered-заказам от суммы товаров и доставки, а не среднее по строкам позиций.
- **Платёжная сумма:** отдельный показатель из `fact_payment`; расхождение с товарами и доставкой сохраняется для сверки.
- **Покупатель:** `customer_unique_id`; заказы разных статусов сохраняются для повторных покупок и анализа отмен.

Формулы, окна, знаменатели, пропуски и неаддитивность перечислены в [паспортах метрик](docs/metric-definitions.md). Поддержка нескольких расчётов не означает, что каждое бизнес-определение уже утверждено командой.

## Сборка и проверки

Для сборки нужны уже работающий PostgreSQL 16+, настроенное подключение и восемь загруженных таблиц `raw`. Владелец загрузки должен остановить всех raw writers на весь запуск. Переменная ниже фиксирует выполненную предпосылку, сама загрузку не останавливает:

```sh
RWB_RAW_RELOAD_PAUSED=1 RWB_DB_MODE=host make build
```

Сборка не запускает Docker и не перезагружает raw. Повторный запуск сохраняет выбранный исходный выпуск; другой выпуск выбирается явно через `RWB_REPORT_RELEASE`. Подключение, права и протокол загрузки описаны в [runbook](docs/build-runbook.md). `scripts/setup.sh` относится к подготовке исходного стенда и перезагрузке raw, а не к ежедневной сборке модели.

**Текущее подтверждение:** на малых синтетических данных PG16.15 прошли 182 шага lifecycle, включая историю, адреса заказа, build/rebuild/rollback и ответы Q1–Q10, с хешами исполняемых SQL. Это не 182 независимые бизнес-гарантии. [Протокол](docs/phase-20261028/evidence/release-final-pg16/summary.json).

**Открытая проверка:** полный запуск текущей модели на Olist, привязка CSV к raw/core и результаты Q6–Q10 из неё ещё не выполнены. Ранее опубликованная [полная mart-выгрузка Q1–Q5](research/implementation-review-20261028/full-model-answers.json) относится к другой версии модели. Независимый CSV-пересчёт, малые SQL-тесты и старая выгрузка имеют разные границы доказательства.

Следующие расширения — события корзины, оплаты, возвратов и выкупа, загрузка изменений и измерение реальной нагрузки. Выбор следующего аналитического движка связываем с запросами, SLA и ресурсами, а не с универсальным «пределом PostgreSQL в строках».
